# MasjidBoard Live Board Discovery Research

**Status:** Historical discovery research; implemented outcome documented separately

## Purpose

Define how MasjidPi will discover the MasjidBoard Live boards that are available to users and generate a catalogue from which a user can select a board.

This is a separate research item from parsing and normalising the data returned by an individual MasjidBoard Live board.

The distinction is intentional:

```text
Board discovery / catalogue
        |
        v
Available MasjidBoard Live boards
        |
        v
User selects a board
        |
        v
Individual board acquisition
        |
        v
Parse / normalise board data
```

MasjidPi should not assume that knowing how to retrieve one board tells us how the complete set of available boards can be discovered.

## Core Requirement

MasjidPi needs a reliable way to:

1. discover the MasjidBoard Live boards that are available;
2. identify the public board identifier (`mid`) for each board;
3. determine the board's display name and other useful catalogue metadata;
4. distinguish Basic/Free boards from Premium boards where the upstream service exposes that distinction;
5. determine whether a board is actually accessible to MasjidPi without requiring unsupported or private access;
6. generate and maintain a local MasjidPi catalogue;
7. allow users to search/select from that catalogue; and
8. subsequently retrieve and parse the selected board using the individual-board provider path.

The catalogue is therefore a discovery product in its own right. It should not be generated by hard-coding a small list of boards discovered manually during parser research.

## Important Architectural Distinction

### Discovery

Discovery answers:

> **Which MasjidBoard Live boards exist and can MasjidPi use them?**

The output is catalogue data.

### Board retrieval

Board retrieval answers:

> **Given a selected public board identifier, how do we obtain that board's current data?**

Current research has established that a Premium board page can expose a public `mid`, a server-supplied opaque `boardId`, and the `theInfo` payload in generated HTML. The opaque `boardId` should remain an upstream implementation detail rather than becoming the user's catalogue identifier.

### Parsing

Parsing answers:

> **What do the returned positional fields mean and how should they be represented in the MasjidPi domain model?**

This remains covered by `MASJIDBOARD-LIVE.md` and the provider research.

These three concerns must remain separate in the architecture.

## Basic/Free and Premium Boards

MasjidBoard Live has at least two board/service categories that must be investigated separately:

- **Basic / Free boards**
- **Premium boards**

MasjidPi must not assume that the same discovery mechanism, page structure, access rules, API behaviour, or available data applies equally to both categories.

The catalogue design should therefore retain an upstream service/category field where useful, rather than flattening all boards into an unexplained single class.

The research must establish whether:

- both categories are publicly discoverable;
- both categories expose stable public board identifiers;
- both categories can be retrieved without authentication;
- Premium-only functionality affects data availability rather than only presentation;
- a board can change category without changing its public identifier;
- disabled, private, expired, or otherwise inaccessible boards can be detected; and
- MasjidPi is permitted to catalogue and retrieve both categories under the upstream service's access model.

## Four Research Stages

### Stage 1 — Upstream ecosystem & board discovery

**Goal:** Determine how MasjidBoard Live exposes the complete population of boards.

Investigate:

- the public MasjidBoard Live site and board directories/indexes;
- Basic/Free board discovery mechanisms;
- Premium board discovery mechanisms;
- links, search results, generated pages, APIs, JavaScript configuration, and other public discovery paths;
- whether there is a canonical upstream board list;
- whether board lists are complete or only represent a subset;
- how public `mid` values are assigned and whether they are stable;
- what metadata is available before retrieving an individual board; and
- how unavailable or removed boards appear.

**Output:** A verified description of the upstream discovery mechanism(s), including their limitations and reliability.

No implementation should be based on a manually collected list until this stage establishes that no better public discovery mechanism exists.

### Stage 2 — Basic/Free vs Premium access and data validation

**Goal:** Establish what MasjidPi can legitimately and technically retrieve for each board category.

For representative boards in each category, verify:

- public page accessibility;
- whether the generated HTML contains board data;
- whether an API endpoint is used;
- whether an opaque `boardId` is exposed;
- whether the same acquisition path works without browser-only state;
- whether the board's core timetable is available;
- whether optional content differs by category;
- whether Premium boards require any additional access mechanism; and
- whether disabled/private/unavailable boards can be distinguished from transient retrieval failures.

The research must also confirm which fields are safe to expose in the catalogue versus which belong only to the individual-board provider.

**Output:** A capability/access matrix for Basic/Free and Premium boards, backed by captures from multiple real boards.

### Stage 3 — MasjidPi catalogue design

**Goal:** Design the local catalogue independently of the upstream 29-row board data structure.

The catalogue should provide enough information for a user to identify and select a board, while avoiding unnecessary upstream implementation details.

Likely catalogue fields include:

- stable MasjidPi catalogue ID;
- public MasjidBoard Live `mid`;
- masjid/board display name;
- alternate name where useful;
- country/region/city where reliably available;
- Basic/Free/Premium service category;
- board availability/access status;
- source/provider identifier;
- last successful discovery/validation time; and
- any additional metadata needed for user search/filtering.

The catalogue should **not** require the opaque `boardId` to be the user-facing identifier.

The design should also decide:

- whether the catalogue is shipped with MasjidPi or generated dynamically;
- whether it can be updated independently of an application release;
- how stale/removed boards are handled;
- how duplicate boards are detected;
- how renamed boards are handled; and
- how search and favourites should operate against the catalogue.

**Output:** A stable MasjidPi catalogue model and update strategy.

### Stage 4 — Implementation, refresh and maintenance

**Goal:** Turn the verified discovery model into a maintainable MasjidPi subsystem.

The eventual implementation should cover:

- discovery acquisition;
- parsing and normalisation of discovered board metadata;
- validation of board accessibility;
- catalogue generation;
- local catalogue storage/cache;
- scheduled or on-demand catalogue refresh;
- safe handling of discovery failures;
- stale/removed board handling;
- user-facing search and selection; and
- integration with the individual-board provider.

The implementation should keep discovery separate from board retrieval so that a failure in catalogue refresh does not prevent an already-selected board from operating from its cached configuration/data.

**Outcome:** The tested catalogue/discovery subsystem was integrated into
MasjidBoard, while preserving manual recovery and last-known-good behaviour.

## Verified Stage 1 Findings

### Public directory endpoint

The public Masjid Search page uses a structured backend endpoint rather than requiring HTML scraping:

```text
POST https://masjidboardlive.com/findmasjid/assets/php/live_page.php
Content-Type: application/x-www-form-urlencoded
```

The captured browser traffic shows a hierarchical discovery flow:

```text
type=country
    ↓
type=province
    ↓
type=cityProvince
    ↓
type=masjid
```

This means MasjidPi can potentially enumerate the directory using structured responses rather than scraping rendered HTML.

The country response includes both names and board counts. At the time of capture, South Africa reported 615 masjids and the directory contained 722 masjids in total across the returned countries.

### Masjid catalogue record structure

A `type=masjid` response returns a city name followed by structured masjid records. Observed fields include:

```text
masjid
fajr_jamaat
zuhr_jamaat
asr_jamaat
maghrib_adhan
esha_jamaat
last_updated
MBL_ID
city
sunset
time_zone_milli
web_url
jumuah_khutbah
ramadhaanactive
date_adjust
moon_seen
ladies_facility
```

The Core directory therefore already contains useful timetable data in addition to discovery metadata.

### `web_url` is the important public slug

Known Premium boards appear in the Core directory with a `web_url` that matches the public Premium `mid` already verified during individual-board research.

Examples:

| Masjid | Core `web_url` | Known Premium page |
|---|---|---|
| Darul Uloom Zakariyya | `zakariyya-park-duzak` | `mid=zakariyya-park-duzak` |
| Masjid Aaisha | `erasmia-aaisha` | `mid=erasmia-aaisha` |
| Madrasah Arabia Islamia / Darul Uloom | `azaadville-darul-uloom` | `mid=azaadville-darul-uloom` |
| Brits Jamia Masjid | `brits-jamia` | `mid=brits-jamia` |
| Masjid Taqwa, Brits | `brits-taqwa` | `mid=brits-taqwa` |
| Fawkner Mosque | `fawkner-masjid` | `mid=fawkner-masjid` |

This relationship has now been observed in both South Africa and Australia.

**Current architectural direction:** Treat `web_url` as the upstream public slug used to correlate a Core catalogue entry with a possible Premium board. Continue to treat the long Premium `boardId` as an opaque implementation detail resolved only when retrieving an individual Premium board.

### `MBL_ID` must remain opaque for now

The Core catalogue also exposes an `MBL_ID`, but the observed suffixes do not map cleanly to Premium vs Basic/Free status.

Known Premium boards have appeared with both `PRM` and `PRP` suffixes:

| Known Premium board | Core `MBL_ID` |
|---|---|
| Darul Uloom Zakariyya | `MBL11300PRM` |
| Masjid Aaisha | `MBL11145PRM` |
| Azaadville Darul Uloom | `MBL11289PRP` |
| Brits Jamia | `MBL11517PRP` |
| Brits Taqwa | `MBL11443PRP` |
| Fawkner Mosque | `MBL11390PRP` |

Other observed catalogue suffixes include `CRM`, `CRP`, `CRS`, `EXT`, and additional `PRM`/`PRP` entries.

Therefore MasjidPi must **not infer Premium status from the `MBL_ID` suffix** unless authoritative upstream evidence is found later. `MBL_ID` should be retained, if useful, only as opaque upstream metadata.

### Stage 1 discovery conclusion so far

The emerging discovery model is:

```text
MasjidBoard Live Core directory
        |
        v
structured discovery endpoint
        |
        v
Core catalogue entry
        |
        +-- masjid name
        +-- geography
        +-- timetable summary
        +-- web_url
        +-- opaque MBL_ID
        |
        v
possible Premium capability probe using web_url
        |
        +-- Premium page resolves
        |       -> richer Premium provider available
        |
        +-- Premium page unavailable
                -> Core/Basic data remains usable if supported
```

This is deliberately independent of undocumented `MBL_ID` suffix semantics.

### Data-quality observations

The discovery layer must tolerate imperfect upstream geography and field values. Captured responses have shown duplicate or blank province entries and special placeholder values such as `~~~~`, `Hide`, empty strings, and `00:00` in timetable-related fields.

The eventual catalogue parser must therefore validate and normalise upstream values rather than assuming that every returned field is clean or complete.

## Research Principles

### Do not confuse examples with a catalogue

The boards already captured in this repository are research fixtures. They prove behaviour for those boards but do not constitute a complete MasjidBoard Live catalogue.

### Do not derive discovery from the parser

The individual-board parser should accept a selected board identifier and parse its data. It should not be responsible for discovering all boards.

### Prefer public, stable identifiers

The public `mid` is currently the appropriate external identifier for a board. The opaque `boardId` discovered inside generated Premium pages is an upstream implementation detail and should not be promoted to the MasjidPi catalogue identity unless later evidence requires it.

### Verify across multiple boards

A behaviour observed on one board must not automatically be treated as a universal MasjidBoard Live rule. Discovery research should sample multiple boards and both service categories.

### Keep access assumptions explicit

If a board is technically reachable but its availability depends on Premium/private/authenticated functionality, that distinction must be recorded rather than silently treating it as equivalent to a public Free board.

### Discovery must tolerate change

MasjidBoard Live may add, remove, rename, disable, or reconfigure boards. The eventual catalogue process must therefore be designed for refresh and reconciliation rather than a one-time scrape.

## Relationship to Existing Research

`MASJIDBOARD-LIVE.md` remains the main research document for the structure and semantics of an individual MasjidBoard Live board, including:

- public `mid` to opaque `boardId` resolution;
- generated HTML and `theInfo` acquisition;
- the 29-row upstream response;
- Jumu'ah mapping;
- Iftar versus Maghrib semantics; and
- normalised provider/domain-model decisions.

This document adds the missing **board discovery and catalogue** research layer.

## Implemented outcome

This research identified the structured public directory and stable public `web_url` identity now used by MasjidPi. The production implementation persists the hierarchy separately, builds location-scoped catalogue partitions, retains Core-only boards and probes Premium only as optional enrichment.

Current discovery behavior is documented in `MASJIDBOARD-CATALOGUE-DESIGN.md`, `MASJIDBOARD-HIERARCHY.md` and `MASJIDBOARD-IMPLEMENTATION-STATUS.md`.
